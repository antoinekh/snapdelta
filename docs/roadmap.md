# Roadmap

The work planned for the next versions of snapdelta. Effort: **S** less than one day, **M** one to three days, **L** more.

| # | Idea | Effort | Status |
|---|---|---|---|
| 1 | **Runners: a plugin architecture for the tasks, with a queue and workers.** A fifth entry point group, `snapdelta.runners`, next to sources, stores, renderers and inventories: the runner executes the tasks of a snapshot (one load per target) and of a diff (one compare per pair). The default runner is the one of today, threads in memory (`--jobs N`, the background jobs of the web server). A plugin gives another runner, such as a queue with workers (Redis, Celery), chosen in `snapdelta.toml` (`[runner] backend = "..."`). A task is data, not a function: the source, the target, the label, or the two references, so that a worker in another process can run it. The worker needs the plugins and the same store, so a file store on one machine does not fit: a shared SQLite file or the PostgreSQL store of item 2. The progress, the results and the errors go through the store and Activity, so the web job page, the CLI and the API work the same with each runner. A first runner plugin, with no external broker, gives scheduled snapshots that run with no person (every night, or before and after each change window): the web UI and the API add jobs to a job table (SQLite), a `snapdelta worker` command takes them and runs them, and `snapdelta schedule` (or cron) adds the jobs at fixed times. | L | Later |
| 2 | **PostgreSQL store**, next to the file and SQLite stores: a third backend of the `snapdelta.stores` entry point group, with the tables of the SQLite store and `psycopg` 3 as an optional dependency (`snapdelta[postgres]`). | M | Later |
| 3 | **Remove `diff --source --file`.** Load the files with `snapshot`, then compare two snapshots: one way to give the right side. | S | To decide |
| 4 | **Diff many targets at once**, for a change on many devices. `snapshot` already fetches many targets in one call (`--target`, `--group`, `--all-targets`), but `diff` compares one pair, so a change window on the group `core` needs one compare per device. Give `diff` the same selection with labels in place of references: `snapdelta diff --group core @before @after` compares `R1@before` with `R1@after` for each host, and `--live` takes the after snapshot of each target and compares it in the same run. One diff per target, run in parallel (`--jobs N`), a summary that lists the targets that changed, did not change or failed, and exit code `1` when one target changed. The same in the web UI (a group or all targets on **New diff**), the API (`POST /api/v1/diffs` with `targets`, `groups`, `all_targets`) and MCP (`compare`), with one run in Activity. | M | Later |
| 5 | **Models by inventory group.** A host gets more models from one of its groups: a router in the groups `frr` and `edge` loads the models of its `frr` source, plus models that only the `edge` routers have (BGP sessions to peers, for example). Today a source has one fixed list of models, and a plugin can only read `self.host.groups` in its own load code. The model declares its groups in the plugin code, next to `_modelname` and `_identifiers`: `_groups = ("edge",)` (or a `@groups("edge")` decorator); a model with no `_groups` is for every host. snapdelta gives the source the models of the host before the load, so the source fetches only those, the snapshot records them, and a compare keeps only the models that both sides loaded, as it already does. **Admin > Models** shows the groups of each model. | M | Later |
| 6 | **Notifiers: hooks after a run.** An entry point group `snapdelta.notifiers`: after a snapshot or a diff, each notifier gets the run (targets, status, errors, has differences, the link to the web UI) and sends it to Slack, Teams, an email, a webhook, or a comment on a change ticket. Many notifiers can get the same event, with one settings table each (`[notifiers.NAME]`) and a filter on the run (only failures, only diffs with differences, a group). A notifier that fails does not fail the run: Activity records its error. | M | Later |
| 7 | **Secret backends.** A `Secret` is a plain value or `{ env = "NAME" }`. An entry point group `snapdelta.secrets` adds other backends, such as HashiCorp Vault, a cloud secret manager or the system keyring: `password = { vault = "net/core#password" }`. snapdelta reads the secret when a source, a store or an inventory needs it, never saves it, and `snapdelta settings` shows only its backend and its name. An inventory can then hold the name of a secret in place of a password. | M | Later |
| 8 | **Auth backends for the web UI and the API.** The modes are `token` and `none` (`[web] auth`). An entry point group `snapdelta.auth` adds OIDC (SSO), LDAP, or the user of a header from a trusted reverse proxy. The user name goes to Activity and to the name on each accepted change, so a shared server knows who did what. | L | Later |
| 9 | **Compare rules from a plugin.** A profile has four fixed kinds of rule: ignore, tolerance, counts and pairs. An entry point group `snapdelta.rules` adds other kinds, such as a case-insensitive compare, the same IPv6 address written in two ways, or a regular expression, and a profile uses them by name: `[profiles.NAME.rules] "interface.description" = "case-insensitive"`. **Admin > Profiles** lists the kinds that the installed plugins give. | M | Later |
| 10 | **A doc on the plugin architecture**, `docs/plugins.md`. The pattern: a microkernel (plug-in) architecture, where a small core finds every implementation through Python entry points, the built-ins included. How snapdelta uses it: each entry point group (sources, stores, renderers, inventories, then the groups of items 1, 6, 7, 8 and 9), its interface, its settings table, how the registry finds it, and what happens when a plugin is missing or fails. How to add a new extension point, and when not to (a second implementation must be planned). Entry points against pluggy hooks: one implementation chosen by name (a store, a runner) or many that get the same event (the notifiers). `architecture.md` keeps a short summary and links to it. | S | Later |
| 11 | **Say "plug-in architecture" on the front page.** The README says that a plugin brings the models and the source, but not that the whole design is a plug-in architecture, extensible by default. Add it to the intro of the README (and a badge next to "built on diffsync"), to the description of the GitHub repository and to the `description` of both packages on PyPI, with a topic `plugin-architecture`. The "Write a plugin" section of the README lists every entry point group and links to the doc of item 10. | S | Later |
| 12 | **Expected changes: check a change against its intent.** Before the change, declare what it must do: a file of expected changes (`vlan 100` added, `interface eth1` `mtu` 1500 to 9000), or the same list in the API and MCP. The diff then gives three lists: the changes done as expected, the expected changes that are missing, and the changes that nobody expected, with an exit code that fails on a missing or an unexpected change. **Accept** stays for a review after the diff; the expected changes are written before it, so a pipeline or an AI agent can check its own work with no person. | M | Later |
| 13 | **Container image.** One image for `snapdelta-web` (and the worker of item 1), with the plugins added in a derived image (`FROM snapdelta`, then `pip install` of the plugins), the settings, the inventory and the store on volumes, and a health check. A compose file for a shared server with a SQLite or PostgreSQL store (item 2). Published on the GitHub container registry at each release, with the PyPI packages. | S | Later |
| 14 | **Ready-made plugins**, so a first snapshot needs no code. Today a user writes the models and a source before snapdelta can read a device: the example plugin and the lab sources only read simulated devices and the containerlab lab. Separate packages on PyPI give the models and the source: `snapdelta-napalm` (many vendors through the NAPALM getters, with the same models for each vendor, so a migration compare works at once), then `snapdelta-openconfig` (gNMI or NETCONF with the OpenConfig models) and `snapdelta-netbox` (an inventory format). Each package has its own dependencies, releases and tests, and keeps the core small. Start with `snapdelta-napalm`. | L | Later |
